# 古诗词库

中华古典诗词搜索 / 浏览站点。数据来自 [chinese-poetry](https://github.com/chinese-poetry/chinese-poetry)（MIT）。

**全站简体。** 原始数据集主体是繁体（唐诗全库繁体），构建时用 opencc 整句转换成了简体。
用户输繁体照样能搜到（搜索层做了繁简变体），只是显示统一为简体。

## 运行

必须用 HTTP 打开（页面靠 `fetch` 读数据，`file://` 不行）：

```bash
cd poetry-web
python -m http.server 8765
# 浏览器打开 http://localhost:8765/
```

## 功能

- **每日一诗**：按当天日期固定推一首，池子是唐诗三百首 366 + 宋词三百首 280。
  同日刷新不变，点「换一首」才随机换。可一键复制或展开详情。
- **搜索**：标题 / 作者 / 诗句全文检索，体裁用胶囊筛选。
  - **繁简互通**：数据显示为简体，但输入繁体照样能搜——搜索时把查询词
    展开成繁简变体再匹配。输「靜夜思」能找到「静夜思」。
  - **排序**：标题精确 > 作者精确 > 标题包含 > 作者包含 > 正文包含。
    搜诗人名时本人作品排前面，不会被「贈蘇軾兄弟」这类标题抢位。
  - **主题检索**：搜「思乡」「送别」「月亮」这类主题词时，该主题的代表作置顶
    并标朱砂角标。古诗里几乎不说「思乡」（古人写「故鄉」「異鄉」「鄉書」），
    纯字面搜索永远搜不到《静夜思》，所以需要这一层。详见下文。
  - 结果上限 500 条，超出会提示加关键词。
- **分类浏览**：唐诗 / 宋诗 / 宋词 / 元曲 / 诗经 / 楚辞 / 论语 / 蒙学。
- **诗人**：唐 / 宋 / 词 各列「存诗（词）最多」50 位，点名字直接搜其作品。
  榜单口径是**收录数量**，不是文学地位——存世量受历史偶然影响很大
  （有人文集散佚，有人被地方志大量收录），所以唐诗榜上会出现「不詳」「無名氏」，
  宋诗榜前列也多是存诗多而非名气大的作者。页面已标注说明。
- **夜间模式**：跟随系统偏好，可手动切换并记住选择。
- **快捷键**：`/` 聚焦搜索 · `Esc` 关详情 · `Enter` 立即搜。

## 设计说明

### 信息架构

搜索框常驻顶栏，首页即可直接搜——搜索是这类站点的第一动作，
不该藏在二级页面里。首页按「主推 → 浏览 → 探索」分三层：
每日一诗做主视觉，体裁导航给入口，热门诗人只放精选 12×3（完整 50×3 在诗人页），
避免一进首页就被 186 个按钮淹没。

### 视觉

宣纸底（`#faf7f0`）+ 墨色字（`#1f1c18`）+ 朱砂点缀（`#a63f2e`），
暗色对应 `#15141a` / `#e9e3d8` / `#d4796a`。

**字体分两套**：诗词正文用宋体（衬线，长文耐读），界面控件用无衬线（清晰）。
字距随字号一起调，诗词正文 `letter-spacing: 1.8~2.5px`、行高 `2.15~2.5`。

**实心填充单独一个令牌 `--seal-solid`**：暗色模式下 `--seal` 会调亮以便当文字色，
直接拿它当按钮底色配白字对比度只有 3.1:1，不达标；所以填充色单独定义，
暗色用 `#a8452f`，白字对比度 5.9:1。测试里有一条断言卡这个。

### 交互

- 详情用**右侧抽屉**而不是居中弹窗：《离骚》300 多行，弹窗读不动；
  抽屉占满视口高度、独立滚动、宽度可控。
- 搜索需要加载数据时给**骨架屏**，不留空白。
- 无结果给**空状态**并提示可换繁简写法，不是干巴巴一句「0 条」。
- 已按体裁筛选时，结果卡片**不再重复显示体裁标签**（纯噪音）。
- 复制失败也会明确告知，不静默。

## 结构

```
index.html          单页应用（样式 + 逻辑都在里面）
data/
  featured.json     每日推荐池 646 首
  poets.json        诗人榜（唐/宋/词 各 50 位，按收录数量降序）
  tags.json         主题标签（取自三百首自带 tags，226 个标签 / 646 首，314KB）
  themes.json       手工补充的主题代表作（宋诗等三百首之外的，129 首）
  inline_data.js    唐诗/宋词/元曲/诗经/楚辞/论语/蒙学（页面直载，27MB）
  song_shards/      宋诗 26 个分片（每片 1 万首）
  t2s_map.js        繁简映射表（只含数据集实际用字，66KB）
build_data.py       从 ../chinese-poetry 重新生成全部数据（繁体）
to_simplified.js    把 data/ 下所有数据整句转简体（opencc）
build_tags.js       从三百首的 tags 生成 tags.json
build_themes.js     把 themes_src.js 的候选对到库内条目，生成 themes.json
themes_src.js       主题候选表（人工维护，改这里再跑 build_themes.js）
make_t2s.js         生成繁简表（需 npm install opencc-js）
test_site.js        回归测试
```

## 几个实现决定

**宋诗不整包加载。** 254,248 首 / 66MB，一次性塞进浏览器会卡死。
拆成 26 个分片，搜索时逐片 fetch、逐片筛，命中到 500 条就停。
分片读过后缓存在内存，重复搜索不再请求。实测搜一个常见词约 1 秒。

**繁简表是自己裁的。** 完整 OpenCC 词典 1.1MB，而数据集实际只用到 14,336 个不同的字。
用 opencc-js 遍历这些字、只留有差异的，得到 4,761 条映射、66KB。

**正文里的方括号清掉了。** 原始数据有 8,072 处 `[爽]節在重九` 这样的缺字标记
（原书表示存疑/异文）。阅读场景下直接去掉括号保留字，读起来才通顺。
这是有损处理——如果需要保留异文信息，改 `build_data.py` 里的 `clean()` 即可。

**全文索引不截断。** 最初为了省体积把正文截到 60 字存进索引，
结果点开详情只能看到前 60 字。实测完整存只多 18% 体积，不值得为这点体积牺牲功能。

**主题层是必须的，不是锦上添花。** 用户搜「思乡」，字面匹配只返回标题恰好叫
《思鄉》《思鄉作》《思鄉嶺》的冷门诗，而《静夜思》《九月九日忆山东兄弟》
《次北固山下》一首都不出现——因为正文里根本没有「思乡」两个字。
数据里有两份可用的主题信息：
- 《唐诗三百首》《宋词三百首》自带 `tags` 字段（646 首、226 个标签，
  「思乡」34 首、「送别」28 首），这是标注好的，作主力；
- 宋诗和三百首之外的靠 `themes_src.js` 人工挑，作补充。

两份合并时**手工的排前面**：标签数据沿用了原书的体裁顺序，直接铺开会让
「橫吹曲辭 出塞」排在「靜夜思」前面。

**元曲要按剧名归并。** 原始数据按曲牌拆开，《醉思乡王粲登楼》有 38 条
（赚煞、混江龙、油葫芦…）。搜「思乡」时这 38 条会把整屏占满，
所以按「剧名・曲牌」的剧名归并成一条，正文按原顺序拼接，详情里能读全剧。

**简体化必须在数据层做，不能前端逐字替换。** 繁简不是一一对应：「乾」在
「乾坤」里读 qián 不能转「干」，在「乾燥」里才转「干」。逐字替换会把「乾坤」
变成「干坤」。opencc 整句转换会看词组，只有它判得准。代价是数据里不再有繁体
原文——需要繁体版本就跳过 `to_simplified.js` 重新构建。

转换后残留约 0.03% 的字会被再次转换，绝大多数是误报（「么」在「什么」里本就
是简体，逐字检查会误判成繁体），真实残留是个位数的异体字。

**两套字段名都要转。** 正文库用 `t/a/p`，而 `featured.json`（每日推荐池）用的是
`title/author/paragraphs`。转换脚本最初只认前者，结果 646 首每日推荐整份漏转，
首页主推的《关山月》一直是繁体。测试里加了逐页扫描（诗人页 / 首页 / 搜索结果）
的断言，就是防这类漏网。

`inline_data.js` 有 27MB，浏览器容易走启发式缓存，所以引用带了版本号
（`?v=2`）。改完数据记得改这个号，否则用户刷新看到的还是旧内容。

**宋词标题要回退到 `rhythmic`。** 宋词原始数据没有 `title` 字段，词牌在
`rhythmic` 里。最初只取了 `title`，导致 21,053 首词标题全空——界面上全显示
「无题」，搜「念奴娇」「水调歌头」什么都搜不到。这个 bug 藏了很久，
直到做主题匹配时才暴露（词牌匹配全失败）。

## 重新构建数据

```bash
npm install opencc-js          # 繁简转换和主题表都需要
python build_data.py           # 正文数据（唐诗/宋诗/宋词/元曲/诗经…），输出繁体
node to_simplified.js          # 全部转简体
node build_tags.js             # 主题标签（读的是简体数据）
node build_themes.js           # 手工主题表（改 themes_src.js 后重跑）
```

## 测试

```bash
# 需要 playwright-core 和 chromium
NODE_PATH=<global node_modules> node test_site.js 8765
```

69 条断言，覆盖首页 / 繁简搜索 / 全文展示 / 排序 / 分类浏览 / 诗人跳转 /
主题检索（名篇置顶、别名映射、元曲归并、宋词词牌回退）/
简体化（乾坤不被转成干坤、诗人名无繁体、逐页扫描无繁体残留）/
边界（空查询、无结果、XSS、分页）/ 布局（按钮不压标签）/ 可用性（常驻搜索框、
主题切换与持久化、`/` 快捷键、复制反馈、抽屉占满高度）/ 视觉（网格无残缺末行、
暗色按钮对比度、标签不重复不拆碎）。

断言都做过变异测试——把实现改回错误版本，确认对应断言会变红，
避免「从没失败过」的空断言。宋词标题那条是直接换回修复前的 `inline_data.js`
跑出来的（21,053 首全空），不是靠推理认定。

两个踩过的坑写在这里，免得重犯：

1. **量 CSS 过渡中间态会假通过。** 暗色按钮对比度那条，第一版在
   `applyTheme('dark')` 之后立刻读 `getComputedStyle`，而按钮有 `.16s` 过渡，
   量到的是中间色，把 3.1:1 误判成通过。切换后必须等过渡结束再读。
2. **截图看不准就查 DOM。** 有次以为标题高亮不一致，实际 `innerHTML` 里
   每条都有 `<mark>` 且背景色相同——是截图缩放造成的错觉。
